# シナリオエディタ改善レビュー

作成日: 2026-11-15

## 結論

目指す方向は「大量のシーンや設定資料から、必要なものをすぐ開き、執筆の文脈を保ったまま作業できるエディタ」。最初に取り組むべきは、左側一覧の共通エクスプローラー化と、画面を切り替えても作業状態を維持する仕組みである。

現状には、階層ノード、折りたたみ、横断検索、資料へのID参照、アウトライン、自動保存、履歴が既にある。土台を活用し、画面ごとに分かれている操作を揃える改善が効果的。単なる配色変更より、探す・開く・戻る・整理する操作の一貫性を優先したい。

本書はソースコードと設計文書の静的レビュー。アプリの改修、実ブラウザ操作、性能計測、テスト実行は行っていない。確認できた実装、推奨仕様、要実測事項を区別して記載する。

## 1. 現状の評価

| 項目 | 確認できた実装 | 改善する理由 |
| --- | --- | --- |
| 執筆一覧 | 階層表示、折りたたみ、同階層ドラッグ、幅変更 | 一覧内の検索・絞り込みがない。幅・展開状態はコンポーネント内の状態 |
| グラフ一覧 | 階層、文字列・タイプ・タグ検索、同階層ドラッグ | 執筆一覧と別実装。タグを全件チェックボックスで表示するため、タグ自体が増えると縦に伸びる |
| 設定資料 | 名称・別名検索、カテゴリ選択、並べ替え | 平面一覧で、ノード一覧と操作体系が異なる |
| 横断検索 | Ctrl/⌘+K、本文・資料・タグ・別名の検索 | 結果は最大40件。結果の該当箇所へ移動する位置情報がない。操作を実行するコマンド機能とは別物 |
| 画面遷移 | 執筆・資料・グラフ・アウトラインの相互移動 | 条件付き表示とローカル状態により、一覧や編集状態が画面をまたいで維持されにくい |
| 参照 | IDによる資料参照、別名、ホバー、使用箇所、参照切れ表示 | 良い基盤。警告と参照先への移動を全体で統一したい |
| 保存 | 自動保存、JSON、過去履歴、競合検出、保存失敗時の救出 | 安全性の土台はある。大容量時の複製処理・履歴容量は要検証 |

主な根拠: `src/components/WritingWorkspace.tsx`、`src/components/graph/GraphEditor.tsx`、`src/components/entities/EntityManager.tsx`、`src/components/CommandSearch.tsx`、`src/domain/search.ts`、`src/app/page.tsx`。

## 2. VS Code / Cursorから採用したい考え方

VS Codeの、画面の役割を分ける構成、Explorer、編集タブ、Quick Open、Command Paletteを参考にする。作品内の大量の情報を扱う際にも、場所・移動・操作を一定に保つ設計が役立つ。[VS Code公式UIガイド](https://code.visualstudio.com/docs/editing/getting-started/userinterface)

Cursorは3.0でAgents Windowを導入し、IDEと切り替えられる構成を案内している。参考にする対象は明確に「執筆に使うIDE型の作業画面」とする。AI機能の追加は今回の情報整理の前提にしない。[Cursor公式3.0変更履歴](https://cursor.com/changelog/3-0)

推奨する画面構成は次のとおり。以下は本アプリ向けの提案である。

| 領域 | 役割 | シナリオ向けの内容 |
| --- | --- | --- |
| 最左の細いナビ | 作業目的を選ぶ | エクスプローラー、検索、構成、グラフ。設定は下部へ |
| 左サイドバー | 対象を探す・整理する | シーン、設定資料、お気に入り、保存した検索 |
| 中央上部 | 作業対象と現在地 | 開いているタブ、章・資料のパス、戻る・進む |
| 中央本文 | 執筆と閲覧 | 本文、資料、グラフを開く。必要に応じて左右分割 |
| 右サイドバー | 選択対象の属性・関連情報 | タイプ、タグ、登場人物、参照元、制作メモ |
| 下部パネル | 横断的な確認 | 問題一覧、検索結果、出力前チェック。通常は閉じる |
| 下端の状態表示 | 保存と執筆の状況 | 保存状態、文字数、バックアップ日時 |

本文を主役にして、右側・下側は必要なときに開く。小画面では同じ情報に一面ずつアクセスできるようにする。

## 3. 左側オブジェクト一覧の具体的な改善

### 3.1 共通エクスプローラーを作る【最優先】

執筆・グラフで同じノード一覧部品と選択状態を利用する。設定資料も検索欄、行の表示、選択、メニューのルールを合わせる。グラフ用の接続設定や整列操作はグラフ側に置き、共通一覧へ混ぜ込まない。

推奨するセクション:

- お気に入り: 作業中の主要シーンやNPCへのショートカット。
- シーン: 初期状態は既存グループを利用したツリー。
- 設定資料: NPC・場所・用語・アイテムのカテゴリ別に折りたたむ。
- 保存した検索: 「未完成」「参照切れ」「アウトライン未配置」など。固定の所属を変えずに横断表示する。

「最近開いた項目」はクイックオープン内に置き、サイドバーの常設項目を増やしすぎない。

### 3.2 整理用フォルダーと章立ての意味を分ける【設計上重要】

現状の `parentGroupId` はグラフ上のグループ関係にも使われている。一方、`OutlineItem` は読み順・出力順の構造で、同じノードを複数箇所に配置できる。

既存グループをツリー表示する第一段階ではデータモデルを変えない。その後、自由な整理用フォルダーが必要なら、本文を持たない独立した整理構造を設ける。整理用フォルダーへの移動でグラフ座標や章の出力順が変わらない設計にする。

UI上は「グループ」「章構成」「整理フォルダー」を識別できる名称・アイコンで表示する。異なる構造を同じ「フォルダー」として扱うと、移動や削除の意味が不明確になる。

### 3.3 一行の情報密度を整える【最優先】

- デスクトップの行高は28〜32px程度を初期案とし、実画面で読みやすさを確認する。
- 展開矢印、種別アイコン、名前、必要最小限の状態表示という順序に統一する。
- 長い名前は省略し、ホバーとキーボードフォーカスで全文を確認できるようにする。
- 常設のドラッググリップを整理し、行自体のドラッグとメニュー操作を用意する。
- 作成・複製・名前変更・移動・削除を行のメニューへ集約する。右クリック以外にも操作ボタンとキーボード経路を設ける。
- 全展開・全折りたたみ、配下件数、現在開いている項目の表示位置への移動を用意する。
- タッチ画面では行高と操作領域を広げる。デスクトップの密度をそのまま適用しない。

### 3.4 探す操作を三つに分ける【最優先】

| 操作 | 目的 | 推奨動作 |
| --- | --- | --- |
| 一覧内フィルター | 表示対象を絞る | 名前・タイプ・タグ。該当項目の親を残し、一時展開して場所を示す |
| クイックオープン | 名前を指定してすぐ開く | 最近使った順、別名、部分一致。同名項目には所属パスを添える |
| 全文検索 | 内容から探す | 該当箇所の抜粋と強調、結果件数、次の結果、本文内の該当位置へ移動 |

フィルター解除後は元の展開状態へ戻す。0件と未作成状態を別のメッセージで説明する。現在の40件制限は「さらに表示」等で利用者に分かる形にする。

ショートカットは既存のCtrl/⌘+Kを尊重して割り当てる。VS Code由来のキーもブラウザの印刷・タブ操作や日本語IMEと競合しないか確認し、画面のボタンからも必ず実行できるようにする。

### 3.5 作業状態を復元する【最優先】

プロジェクト単位で、展開状態、一覧幅、選択項目、スクロール位置、フィルター、開いているタブを保持する。検索や内部リンクで項目を開いたときは、祖先を展開して選択行を可視範囲へ移す。

共有すべき整理フォルダーや名前付き検索はプロジェクトデータ、端末固有の幅・展開・スクロール位置は表示設定として分ける。削除済みIDを復元しようとした場合の代替表示も決める。

### 3.6 件数が増えたときの操作と性能【次段階】

複数選択、一括タグ変更、一括移動、移動先検索を追加する。既存のタグ管理機能を活用し、選択中の対象から実行できる導線を整える。親変更は循環を禁止し、移動先と操作結果を明示する。

多数行は画面内の行だけ描画する方式を検討する。ただし先に計測し、フォーカス移動・検索結果への移動・支援技術対応を維持できる実装を選ぶ。

| P2 | 進行・閲覧モード | 卓で使う読み上げ、KP情報、手掛かりの確認に最適化。編集画面とは別の表示プリセットにする |

### 章単位出力の具体的な指摘

`exportMarkdown()` は、指定章の次に出現する同じ深さの項目までを切り出す。例えば「第1章（深さ0）→節A（深さ1）→第2章（深さ0）→節B（深さ1）」で節Aを選ぶと、第2章の見出しも出力範囲に入るロジックになっている。

終了条件を「指定章の後にある、同じ深さまたはより浅い項目」にする必要がある。第2章に本文が紐付いていれば、その本文も範囲外から混入し得る。最終節の出力、親章への復帰、深い孫節を含むケースで回帰テストを追加する。これはコード上の指摘であり、今回実行再現はしていない。

### 大容量時の重点調査箇所

- `WritingWorkspace.tsx` と `GraphEditor.tsx`: 毎描画で親子マップを再構成し、兄弟配列を繰り返しコピーしている。全展開時の行数も計測する。
- `search.ts`: 検索ごとに本文を走査し、型・タグ・文書を配列検索する。ID索引と変更文書単位の検索索引更新を検討する。
- `autosave.ts`: キュー投入ごとに全体を複製する。保存の500ms待機はこの複製コストを減らさない。
- `database.ts`: 過去スナップショットを蓄積し、履歴取得は全件を読み込む。件数と本文量を増やして時間・容量を測定する。
- `GraphHistory`: 最大100件の全体スナップショットを保持する。Undoの改善時にメモリ使用量も評価する。

これらは性能リスクであり、現時点で遅延を実測したという意味ではない。差分保存への全面移行は、整合性と復元の複雑さも踏まえて判断する。

## 5. 推奨する実装順

1. **出力の正確性**: 章単位出力の境界を修正・検証する。
2. **左一覧の第一段階**: 既存グループを維持した共通ツリー、執筆側フィルター、状態保持、現在項目の表示、コンパクトな行とメニューを実装する。
3. **執筆の往復**: 編集タブ、戻る・進む、カーソル位置復元、資料の固定表示を追加する。
4. **大規模整理**: 独立フォルダーの要否を決め、保存検索・複数選択・一括移動を追加する。計測に基づいて描画・検索・保存を改善する。
5. **シナリオ制作支援**: 問題一覧、出力前チェック、制作状態、伏線、進行表示を段階的に追加する。

第一段階ではモデルの大幅変更を避け、操作改善の効果を確認する。自由な整理フォルダーを導入する段階では、既存JSONの移行とID参照維持を検証する。

## 6. 改善後の受け入れ条件

以下の性能値は提案する目標であり、現在の実測値ではない。実際に利用するPCとブラウザを基準環境として記録する。

| 確認対象 | 合格の目安 |
| --- | --- |
| 大量の一覧 | 1,000シーン・300資料・200タグ、最大8階層のデータで、絞り込み・移動・展開が実用的。代表操作の95%が100ms以内に視覚応答することを初期目標とする |
| 全文検索 | 日本語本文合計100万字の試験データで、入力後300ms以内の結果表示を初期目標とする。超過時は入力を阻害しない進行表示を行う |
| 作業復帰 | シーン→資料→グラフ→シーンで選択・本文位置・一覧展開が維持される。再起動後も保存対象の表示設定が戻る |
| 検索中の階層 | 閉じたグループの子が検索に一致しても到達でき、解除後は元の展開状態に戻る |
| 同名オブジェクト | 所属パスと種別で区別でき、名前変更・移動後もID参照が維持される |
| 日本語入力 | IME変換確定が検索結果の決定と混同されない。入力直後の画面移動でも本文が欠落しない |
| キーボード・タッチ | マウスのドラッグなしで移動・並べ替えができる。フォーカスが常に判別できる |
| Undo | 対象操作を一回戻したとき何が戻るかが一定で、別画面での編集内容を意図せず消さない |
| 保存と復元 | 保存失敗、再読み込み、競合、履歴整理後も退避・復元が可能。履歴容量の増加を測定する |
| 出力 | 指定章の配下のみを出力し、より浅い次章を含まない。出力から除外されるシーンを事前確認できる |

## 7. 判断

このアプリの強みは、本文・グラフ・設定資料・章構成が既に同じ作品データに結び付いていること。まずそれらを行き来する体験を揃えると、シナリオ特化エディタとしての価値が伝わりやすくなる。

最初の改修単位は「共通エクスプローラー＋状態保持＋検索導線」を推奨する。完了判定は、見た目の類似ではなく、数百件に増えても目的の場面を探し、参照し、元の執筆位置へ戻れることとする。
