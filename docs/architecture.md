# アーキテクチャと設計判断

## 範囲と前提

2026-11-09。初期版は個人利用。今回の成果物はPhase 1のローカル開発用アプリであり、外部公開・GitHub連携は行わない。既存アプリがないためワークスペース直下にNext.js App Routerで作成した。

不明点はPhase 1を妨げない前提で保留する。GitHub Appの所有者・導入先・公開サーバーの所在、PDFの用紙サイズ・フォント、将来の巨大プロジェクト規模、グループノードの外観は該当フェーズ開始時に確定する。

## レイヤー

UI → ドメイン操作／自動保存 → Repository → IndexedDB。

ドメインにReact・Dexie・React Flow・Tiptapを持ち込まない。Repositoryと自動保存はUIに依存しない。Phase 1はReactの状態管理だけで足りるためZustandは未導入。CSSも小規模なためTailwind/shadcnは未導入。後続フェーズで必要性を再評価する。

## 保存モデル v1

Project、ScenarioNode、ScenarioEdge、NodeTypeDefinition、FieldDefinition、ScenarioEntity、EntityAlias、Tag、OutlineItem、SyncMetadataをそれぞれ独立したZodスキーマと推論型として定義。加えてDocumentを定義し、本文をノードへ埋め込まずdocumentIdで関連付ける。構造化本文のルートはContent[]。

- UUIDは各プロジェクト内で一意・不変。JSONの復元コピーではProjectだけ新IDにし、内部のID参照は維持する。別プロジェクト間参照は扱わない。
- フィールド値は判別可能なunionで型付けし、Field IDをキーに保存。タイプ変更やフィールド非表示で残存値を削除しない。タイプ定義にない旧フィールド値も保持する。
- フィールド順序は定義配列、選択肢はIDと名称。後続の削除UIでは確認と退避を行う。
- ノードのpositionとOutlineItemのparentId/orderは別管理。同じノードを複数OutlineItemから参照できる。未登録ノードも維持する。
- エッジは多重接続・循環を許可。親グループとアウトラインの階層循環は禁止。
- 本文の保存形式は独自のContent union。Tiptapの内部JSONを正本にはしない。Phase 3で双方向アダプターを実装し、非対応要素を破壊的に落とさない往復試験を追加する。
- エンティティ参照はentityIdを常に保持し、aliasではaliasId、fixedでは固定表示文字列を追加する。本文の文字列置換は行わない。
- 削除された本文・カスタムフィールド内のノード／エンティティ参照は将来の警告対象として保持する。一方、エッジ・アウトライン・本文所有者の構造参照切れは保存時に拒否する。全使用箇所の走査・UI警告はPhase 3で追加する。
- 初期ノードタイプは本文・イベント・情報・設定資料。エンティティカテゴリは拡張可能な文字列とし、NPC・場所・用語・アイテムの選択UIはPhase 3で実装する。

全スナップショットにschemaVersion:1を持たせる。strictObjectにより未知項目を黙って削除しない。未知版・不正データは書き込み前に拒否し、原本を保持する。読めないプロジェクトがある場合は初期化で上書きせずエラー表示して停止する（個別隔離・生データ救出UIは追加課題）。

## 保存・復元と競合

IndexedDB名はtrpg-scenario-editor。projectsに最新スナップショット、historyに[id+revision]ごとの過去スナップショットを保存。独立モデルを集約した一つのスナップショット単位で永続化することで、本文・ノード等の途中状態を避ける。正規化テーブルへの分割は規模に応じて後から判断する。

1. 500msデバウンスで最新編集をキューに格納。
2. 保存直前にスキーマと構造整合性を検証。
3. readwriteトランザクション内で既存revisionとexpectedRevisionを比較。
4. 既存状態を履歴に保存し、新状態と増分revisionを同時に保存。
5. 成功した保存だけrevisionを進める。保存中に発生した編集は続けて保存。

失敗時は最新の未保存スナップショットをメモリに維持し、再試行かJSON退避を提供。別タブ更新の競合では自動上書きしない。プロジェクト切り替え・新規作成・履歴復元は現在の保存成功を待つ。履歴復元も通常の新リビジョンとして保存し、復元前の状態も履歴に残す。

JSON取り込みは検証後、別Project IDで新規保存。同期メタデータは初期化し、コピーから元のGitHubデータを更新しない。

履歴の自動間引きは未実装。容量不足時に履歴を無断削除しない。大容量データの差分保存・圧縮・明示的な履歴整理は将来検討する。

## マイグレーション方針

現在の保存形式はv1のみで既存版からの移行は存在しない。未検証の自動移行は行わない。v2導入時は純粋なv1→v2変換関数、原本バックアップ、移行後検証、参照保持・復元テストを必須とし、明示的な移行操作で新コピーへ保存する。IndexedDBストア版とJSONのschemaVersionは別管理。

## 外観設定

ライト／ダーク表示、サイト全体のアクセント色と背景色、カラー履歴、グループごとの色は表示上の設定としてブラウザのlocalStorageへ保存する。シナリオ本文や構成データではないため、プロジェクトJSONには含めない。背景色から各画面のカード、パネル、入力欄、選択面の色を導出し、個別の色調を一括して変更する。グループ色はプロジェクトIDとグループノードIDに紐づけ、他のプロジェクトへ影響させない。色履歴は各カラーピッカー間で共有し、直近8色を保持する。

## GitHub同期の予約設計（未実装）

Phase 5でサーバー側GitHub App認証を採用する。秘密鍵・ユーザートークン・installation tokenをブラウザへ返さない。Secure/HttpOnlyセッション、CSRF保護、認可チェックを設ける。リポジトリはprivateのみ選択可能とする。

プロジェクトスナップショットとbaseCommitShaを基に変更を判定。Git Data APIのtree/commit作成後に参照を非force更新し、複数ファイルを一つのcommitとして可視化する。同期を単一キューで処理し、リモート先行時は競合扱いとしてローカル・リモート・baseの3状態を保存する。同期開始後の追加編集を同期済みにしないよう、同期対象ローカルrevisionを固定する。競合・通信失敗でローカルデータを置換しない。この方式は実装時にAPI仕様を再確認する。

## オフラインとUI

編集とローカル保存にAPI通信は不要。アプリシェルをオフライン起動するキャッシュ、更新時の安全性、PWAはPhase 6。Phase 1の画面はプロジェクト一覧・概要・保存情報で構成し、小画面では縦積みにする。完成版の3ペイン・4タブ・タッチ接続・リサイズは後続フェーズで実装する。

## 検証上の限界

fake-indexeddbは実ブラウザの永続性やOS終了を再現しない。実ブラウザで日本語の入力・保存・再読込は確認したが、実機モバイル、IME入力中の切り替え、容量上限、長文性能、オフライン起動、全バックアップ操作のE2Eは今後の検証対象。

## Phase 2の実装

React Flowとの変換はsrc/components/graph/adapter.tsに隔離。保存座標は絶対座標のまま維持し、表示時だけ親に対する相対座標へ変換する。ドメイン操作はsrc/domain/graph.tsに分離。ノード削除時は関連エッジを除去し、アウトラインの見出しは残してnodeIdだけ解除、本文Documentは保持する。複製は本文とリッチテキストフィールドのDocumentも複製する。Undo/Redoはセッション内100操作で、永続保存履歴とは別管理。今回33件の単体テスト・型チェック・ビルド成功。実ブラウザでのグラフ回帰検証は未実施。
